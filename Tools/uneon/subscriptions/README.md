# Подписки UNEON: первая тестовая версия

Статус: основа для проверки привязки и прав. Игровых наград пока нет.
По умолчанию интеграция выключена. Код Dead Space не использован.

## Устройство

- Boosty назначает роли подписчикам в Discord штатной интеграцией.
- На VPS `service.py` хранит привязки SS14 UUID ↔ Discord ID в SQLite и проверяет
  роли через Discord REST API. На игровой машине Discord не требуется.
- Расширение `discord_extension.py` подтверждает одноразовые коды через существующего
  discord.py бота. Оно не запускает второго бота и не изменяет мониторинг.
- Сервер игры обращается только к VPS. HTTPS обязателен, кроме loopback-адреса
  при разработке или использовании защищённого SSH-туннеля.
- Секрет игрового сервера даёт доступ к привязкам: хранить как секрет, не выдавать клиенту.

## Контракт и правила

`Authorization: Bearer <UNEON_API_KEY>` обязателен для всех HTTP-методов.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/v1/link-code` | JSON `{"user_id":"SS14 UUID"}` → код на 10 минут |
| GET | `/v1/entitlements/SS14-UUID` | Уровень и список разрешений |
| POST | `/v1/unlink` | JSON `{"user_id":"SS14 UUID"}` → удалить привязку |

Подтвердить код можно только через Discord-расширение, публичного HTTP-метода нет.
В игре UUID берётся из сессии отправителя, а не аргумента команды.
Один Discord-аккаунт связывается только с одним SS14-аккаунтом и наоборот.
Для смены привязки требуется сначала выполнить отвязку из игры.
Новый код отменяет предыдущий; код хранится в виде SHA-256, используется один раз.
Подтверждение и потребление кода выполняются одной SQLite-транзакцией.

Учитывается **самый высокий** из настроенных уровней. Его `permissions` должен
содержать полный список прав, включая желаемые права предыдущих уровней.
ID роли и ID Discord-сервера — числа, не названия и не ID канала.
Файл `tiers.example.json` намеренно неработоспособен до замены ID роли.

Подключённые игроки проверяются примерно раз в 2 минуты; команда проверки — сразу.
Подтверждённое отсутствие роли даёт tier 0 и удаляет старые права.
Ошибка/таймаут/429/неверный токен не считаются подтверждением отсутствия подписки.
При сбое игровые права из последней успешной проверки действуют до 6 часов
(настраивается, максимум 24 часа). Повторные ошибки срок **не продлевают**.
Кеш сохраняется в `--data-dir/uneon-subscriptions.json` и переживает перезапуск.
Этот срок — допустимая задержка отзыва при сбое, а не реальная дата окончания Boosty.
Недоступность сервиса не мешает обычной игре, но новые права не подтверждаются.
Состояние без подтверждённой копии не даёт привилегий.

## Локальная проверка (не требует Discord или токенов)

Из корня репозитория:

```powershell
python -B -m unittest discover -s Tools/uneon/subscriptions -p test_service.py -v
```

Тесты используют временную БД, поддельный Discord и HTTP на loopback.
Они не отправляют сообщения, не меняют роли и не подключаются к реальному сервису.

## Развёртывание VPS — после настройки ролей и доступа

1. Проверить, что VPS имеет доступ к `https://discord.com/api/v10`.
2. Скопировать `service.py` в `/opt/uneon-subscriptions/`.
3. Создать системного пользователя `uneon-subscriptions` без интерактивного входа.
4. Создать `/etc/uneon-subscriptions/tiers.json` на основе примера и заполнить роли.
5. Создать `/etc/uneon-subscriptions/subscriptions.env` на основе примера.
   Генерация API-ключа: `python3 -c 'import secrets; print(secrets.token_urlsafe(48))'`.
   Файл окружения хранить root-only (0600), не в Git.
6. Установить `uneon-subscriptions.service` в `/etc/systemd/system/`.
   После проверки конфигурации: `systemctl daemon-reload`, затем
   `systemctl enable --now uneon-subscriptions`.
7. Сервис слушает **только 127.0.0.1:8787**. Не открывать этот HTTP-порт в интернет.
   Настроить TLS reverse proxy до него или защищённый туннель с игровой машины.
8. Включать интеграцию игры только после проверки этой связи.

Пример Caddy для уже принадлежащего вам домена (A/AAAA должны вести на VPS):

```caddy
subscriptions.example.org {
    reverse_proxy 127.0.0.1:8787
}
```

Настройку VPS, DNS и доступности HTTPS проверять отдельно; шаблоны сами ничего не устанавливают.
Резервировать `links.db` через SQLite backup API: это отдельная БД на VPS,
существующий бэкап игрового сервера её не включает.

## Подключение к существующему боту

Нужно сначала проверить исходники и библиотеку бота. Модуль рассчитан на discord.py 2.x.
Не заменять существующий основной файл бота и не синхронизировать пустое дерево команд.

Если репозиторий доступен боту как Python-путь, в его `setup_hook` загрузить:

```python
await bot.load_extension("Tools.uneon.subscriptions.discord_extension")
```

Использовать существующий порядок `CommandTree.sync`; если команды синхронизируются
на конкретный guild, перенести туда и `uneon_link` тем же способом, что остальные команды.
Расширение регистрирует команду только в `DISCORD_GUILD_ID`.
Расширение само `sync` не вызывает, чтобы не удалить команды мониторинга.
Окружение бота должно содержать `UNEON_DB` и `DISCORD_GUILD_ID`.
Расширение и сервис обязаны читать **один и тот же** файл SQLite и иметь к нему доступ.
Сначала определить пользователей systemd-служб и настроить ограниченную общую группу/
каталог. Не делать БД общедоступной и не запускать бота под root ради доступа к ней.
Токен REST-провайдера может принадлежать этому же боту: сервис не открывает Gateway.
Сервис поддерживает systemd `LoadCredential=discord_token:ПУТЬ_К_СЕКРЕТУ`:
он читает `discord_token` из `CREDENTIALS_DIRECTORY`, как существующий монитор.
Дублировать токен в env-файле не нужно.
Файл уровней также можно передать через
`LoadCredential=subscription_tiers:/etc/ss14-monitor/subscription-tiers.json`.
Эта копия имеет приоритет над `UNEON_TIERS_FILE` и не требует разрешения прохода
пользователю службы в закрытый каталог `/etc/ss14-monitor`.
Бот должен быть участником нужного Discord-сервера. Полномочия администратора и
управление ролями нашему сервису не требуются; роли выдаёт интеграция Boosty.
Не использовать вручную выдаваемые всем роли как роли подписки.

### Установленный ss14-monitor на VPS

Для подтверждённого ниже окружения подготовлен `install_monitor.py`.
Скопировать эту папку на VPS и выполнить от root:

```bash
python3 /root/uneon-staging/subscriptions/install_monitor.py
```

В нём настроены Discord guild `1571189014478848020`, роль первого уровня
`1572636208310526132` и источник credential `/etc/ss14-monitor/discord_token`.
Установщик проверяет окружение, делает копию bot.py, добавляет безопасный hook,
создаёт ключ API без вывода и готовит systemd-службу. Он **не перезапускает** службы.
Повторная установка сохраняет существующий ключ и настройки ролей.
При неизвестной структуре bot.py или изменившейся конфигурации отказывается от установки.
После сообщения `Staged successfully`:

```bash
systemctl daemon-reload
systemctl enable --now uneon-subscriptions
systemctl restart ss14-monitor
systemctl is-active uneon-subscriptions ss14-monitor
journalctl -u uneon-subscriptions -u ss14-monitor -n 40 --no-pager
```

Ключ API хранится в `/etc/ss14-monitor/subscriptions.env`, root-only. Не публиковать.
Встроенный hook регистрирует guild-команду, проверяет удалённые команды перед sync
и не даёт сбою интеграции остановить запуск мониторинга. Отдельный файл пакета
`host_setup.py` вызывается только при `UNEON_SUBSCRIPTIONS_ENABLED=1`.
Откат интеграции бота без изменения его мониторинга: выставить
`UNEON_SUBSCRIPTIONS_ENABLED=0` в `/etc/ss14-monitor/subscriptions-bot.env`
и перезапустить только `ss14-monitor`. Можно также вернуть сохранённую копию bot.py.
Удалённая slash-команда при выключении может оставаться видна до отдельного удаления.

Подтверждённая конфигурация: `/opt/ss14-monitor/bot.py`, пользователь `ss14-monitor`,
`ProtectSystem=strict`, `StateDirectory=ss14-monitor`.
Модуль следует разместить как пакет `/opt/ss14-monitor/uneon_subscriptions/`
и загрузить через `await self.load_extension("uneon_subscriptions.discord_extension")`.
Общая БД: `/var/lib/ss14-monitor/subscriptions/links.db`.
Отдельную службу API запускать от `ss14-monitor` с `StateDirectory=ss14-monitor`.
Обе службы получают одинаковый `UNEON_DB` и ID Discord-сервера.
Секрет API нужен только службе API и игровому серверу, боту привязки он не нужен.
Источник `LoadCredential` сначала посмотреть через
`systemctl show ss14-monitor.service -p LoadCredential`; не выводить содержимое секрета.
После загрузки расширения host-бот синхронизирует guild-команды через
`await self.tree.sync(guild=discord.Object(id=int(os.environ["DISCORD_GUILD_ID"])))`.
Перед первым sync проверить удалённые команды и отказаться от синхронизации,
если локальное дерево не содержит ранее зарегистрированных команд.
Существующие polling, уведомления, HTTP-сессию и `read_token` сохраняем.

## Конфиг игрового сервера

Добавить в `/opt/uneon/config/server.toml` (после публикации игровой сборки с этим кодом):

```toml
[uneon_subscriptions]
enabled = true
api_url = "https://subscriptions.example.org"
api_key = "ТОТ_ЖЕ_СЕКРЕТ_ЧТО_НА_VPS"
grace_minutes = 360
```

Секрет не коммитить. Готовый live-конфиг сервера сейчас не изменён.
Для тестового SSH-туннеля допустим `http://127.0.0.1:8787`.
Сохранённые права читаются только сервером. Клиент не сообщает свой уровень подписки.

## Проверка игроком

В игровой консоли:

```text
uneon_subscription link
```

В Discord UNEON:

```text
/uneon_link code:ПОЛУЧЕННЫЙ_КОД
```

Ответ бота виден только этому игроку. Затем в игровой консоли:

```text
uneon_subscription
```

Для удаления своей привязки:

```text
uneon_subscription unlink CONFIRM
```

Тестируем: выдачу роли, снятие роли, неверный/просроченный/повторный код,
потерю Discord на VPS, потерю VPS для игры, перезапуск игры с кешем.
Только после этого подключаем отдельные игровые бонусы через
`UneonSubscriptionsSystem.HasPermission(userId, "permission")`.
Игровые награды и их защита от повторной выдачи пока не реализованы.
